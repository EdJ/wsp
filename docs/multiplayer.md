# wsp multiplayer: a small hub and a local wsp per person

Nov 24, 2026 · @Jesper · Hub and spoke, as built

Two people, Jesper and Ed, work on one project with their own agents, each on their own machine, and see and hand each other's work. This document is how that works. The design of record is the Claude Doc of this name; the decisions are the wsp project's d5, d6 and d7 (`wsp project show wsp --decisions`). The earlier design, one wsp server for an org of groups, is retired: it is under "Later", and the old text is in git (`git show fdade73:docs/multiplayer.md`).

## Purpose

The collaboration this serves is the one between two people who each already run wsp:

- **Each keeps their own wsp.** Daemon, manager, seats, worktrees, checks and builds run on the person's machine, as today. A wsp with no hub works exactly as it always did.
- **They share what they choose to.** A row or a worklist that both should see, take and drive lives in a shared workspace. Everything else stays on its owner's machine and is never sent.
- **One place agrees who holds what.** Who has a row, who drives a list, who is allocated what, and where a message goes are decided by one small hub, not by two machines guessing.
- **Joining, leaving and offline are normal.** Nothing here makes a wsp depend on the hub: a person works alone, joins, goes offline mid-row and syncs back.

The hub hosts no agents and runs no builds (d5). Code moves between the people through their shared git remote, never through the hub.

## Hub and spokes

```
 Jesper's machine                         Ed's machine
 ┌──────────────────┐                    ┌──────────────────┐
 │ wsp (a spoke)    │                    │ wsp (a spoke)    │
 │ daemon · manager │                    │ daemon · manager │
 │ seats · worktrees│                    │ seats · worktrees│
 │ private rows     │                    │ private rows     │
 │ synced cache     │                    │ synced cache     │
 └────────┬─────────┘                    └─────────┬────────┘
          │  TLS, a per-user token                 │
          └──────────────►  wsp-hub  ◄─────────────┘
                     objects · refs · leases
                     users · tokens · message queues
```

**The hub** is a program of its own repository, `wsp-hub` (`wsp-hub serve --config <file>`; the domain is its `crates/ledger`), a separate binary that wsp neither contains nor links. It holds four things in one data directory:

- `objects/`: every record and event, each in a file named by its hash.
- Refs: per shared workspace, which object is each subject's head.
- Leases, with their fencing tokens, in its SQLite database.
- Users, tokens and each user's message queue, in the same database.

wsp's side of it is the spoke (`crates/spoke`) and the wire they share (`crates/hub-protocol`). The hub's behaviour named below is the hub repository's; paths named here are wsp's.

**Testing against it.** The tests that need a real hub (the spoke's and the root's `tests/{privacy,identity,login,hub_sync,hub_cache,publish,publish_sync}.rs`) run the hub's own program through `wsp_spoke::testhub`: `WSP_HUB_BIN=<path to wsp-hub>` runs the binary as a child process on loopback, `WSP_HUB_IMAGE=<image>` runs its container image over TLS with a throwaway CA. Without either they are skipped, with one notice per test binary; `WSP_HUB_REQUIRED=1` makes that a failure. A lease's TTL passes in real time there (`lease_secs`), and what a test reads of the hub it reads over the wire or from the hub's data files.

**A spoke** is a person's ordinary wsp, once it is logged in (`wsp login`, below). Logging in adds one thing: the daemon starts the sync worker, a thread named `hub-sync` (`crates/spoke/src/hub_sync.rs:162`, started by `start` at `crates/spoke/src/hub_sync.rs:182`) that takes turns only while `~/.config/wsp/hubs.json` exists and the connection is switched on. `wsp hub disable` stops this wsp taking part in shared work and keeps the login: the switch is written first (no new lease, no shared list advanced from here, a row filed shared kept provisional on a local id until enabled, no message sent), the shared rows with agents in flight are parked with `wsp park`'s write, and the agent of each live seat on one is ended when its current turn is over with the engine's own despawn (`end_seat_when_idle`: a detached `wsp despawn --pane <seat> --keep-tree` that waits, up to twenty minutes, until the seat is not mid-turn; the worktree is kept and the row stays parked), the journal is flushed while the hub answers, the row and drive leases are given back (a row whose agent is still finishing keeps its lease until that agent's claim ends, so nobody else leases a row an agent is still writing to; `wsp hub status` says which agents are finishing and, afterwards, which rows had their agent ended; private rows and their agents are untouched), and the worker takes no further turn, the cache readable and marked not live (`link: off` in `sync.json`). A hub that does not answer leaves the journal kept and the leases to run out. `wsp hub enable` switches back on (the worker's next look replays the journal) and takes each parked row's lease again: granted, the row returns to its recorded status with no agent started (it is ready to be started again, and a member of a list this wsp drives is reseated by the run once it has been without a seat for `SILENT_AFTER`); held by another user, it stays parked and says who holds it; a row whose agent is still finishing stays parked until it has ended. The switch and the parked rows are `$WSP_STATE/hub/switch.json` (`crates/spoke/src/hub_switch.rs`). Logging out disables first, then removes the login file (`hubs.json`) (an agent still finishing its turn then ends with no login to give its row's lease back with, so that lease runs out, and logout says so); the switch stays off and keeps the rows the disconnect parked, so `wsp hub status` with no login says only that and the way back (`wsp login`, then `wsp hub enable`), and a later login says the connection is off. Without a login no hub code runs and nothing is written.

**The worker's turn** runs every 10 seconds (`TURN`, `crates/spoke/src/hub_sync.rs:165`; `$WSP_HUB_SYNC_MS` changes it) and at once when a task file changes. It takes each task of a shared workspace, makes a record of it if its file moved since the synced head, journals that record, and syncs through the spoke's own hub client, `hub_client::Client::sync` (`crates/spoke/src/hub_client/sync.rs:331`). A hub that does not answer is a state, not a failure (a hub that answers and refuses the login, a revoked or unknown token, is another: the link reads `refused` in `sync.json`, `cycle.log` says `the hub refused this login` once, and `wsp hub status` and `wsp whoami` say so; a workspace the hub will not sync, as `forbidden` for a non-member, is listed under `refused` in `sync.json` and in `wsp hub status`): one line in `cycle.log` when it changes, then another try after a wait that doubles from 1 s to 60 s (`BACKOFF_MIN`, `BACKOFF_MAX`, `crates/spoke/src/hub_sync.rs:171`).

**The wire** is `wsp-hub-protocol` (`crates/hub-protocol`, the contract the spoke and the hub share, held byte for byte to the frames `wsp-api` carried while the hub ran inside wsp, `tests/golden`): the spoke's client (`crates/spoke/src/hub_client`) speaks it and nothing else. The hub's verbs are `sync.heads`, `sync.have`, `sync.put`, `sync.get`, `refs.move`, `ids.alloc`, `lease.take`, `lease.renew`, `lease.release`, `msg.send`, `msg.take`, `msg.ack`, and the identity commands `hub.user.add`, `hub.user.revoke`, `hub.token.issue`, `hub.token.revoke`, `hub.workspace.add` and `hub.member.set` (`crates/hub-protocol/src/sync.rs`, `crates/hub-protocol/src/identity.rs`). The hub's port is 7489, the one after the daemon's own API. The daemon's server admits loopback and the tailnet only, and serves no hub verb (a hub verb is unknown to it); the hub's peer list is its own.

## Hash sync

The hub is content-addressed and synced by comparing hashes, git-like (d6). The format is `crates/objects/src/lib.rs`.

- **An object is immutable.** One is a version of an entity (`Object::Record`, `crates/objects/src/lib.rs:135`: a row, a list, a seat, whole, with its `parent` version) or one thing that happened (`Object::Event`). Its `ObjectId` (`:56`) is the SHA-256 of its canonical bytes (sorted keys, no whitespace; `encode` at `:195`, `verify` at `:222`), so there is no update: a change is a new object whose parent is the old one. An id names one sequence of bytes, so an object can be cached anywhere and is stored once however many spokes send it.
- **Refs are the only thing that moves.** `Refs` (`:284`) say, per workspace, which object is each subject's head. Two sides sync by comparing refs (`diff`, `:370`) and sending only the objects behind the subjects that differ.
- **A move is a compare-and-swap.** `refs.move` names the head it expects. Of two moves from one head exactly one is written, in one `BEGIN IMMEDIATE` transaction; the other is answered `ok` with the hub's head and the word `stale` (the hub's `lib`, `Hub::move_ref`). It is never retried over the hub.
- **A stale edit is merged, not lost.** The spoke takes the hub's head through the door and merges three versions: the common ancestor (found through parents), its own file and the hub's head (`crates/spoke/src/reconcile.rs`). A field changed on one side takes that side; the `## Log` and `## Decisions` sections are the union of both sides' dated entries; a field changed on both keeps the hub's and writes the spoke's value into the log as a conflict note, tagging the row for its user. The merge is pushed as a new object whose parent is the hub's (`crates/spoke/src/hub_sync.rs:148`, `after_stale`).
- **Ids are the hub's.** `ids.alloc` hands out a row's id from one counter per project, never reused, so two spokes cannot make the same id (the hub's `lib`, "Ids"). Every shared row takes its id from it: a row published (`wsp publish`) and a row filed directly as shared (`wsp add --workspace shared:<name>`, or a sub-task of a shared row) alike, asked through the add-on interface (`SharedWork::new_row_id`, `crates/spoke/src/hub_ids.rs`) before anything is written, so a refusal writes nothing. A private row, and a wsp with no login, take the local counter. A row filed shared while the hub does not answer, or while the connection is switched off, takes a local id and is *provisional* (`$WSP_STATE/hub/provisional.json`; `not yet published` in `wsp ls` and `wsp show`, counted in `wsp hub status`): never pushed and never leased under that id, its sub-tasks provisional with it. The first turn that reaches the hub takes hub ids for them and renames them the way publish does (old ids recorded in `ids.json`; pieces, sub-tasks, list members, legs, claims and seat bindings follow; a claimed row is leased at its new id), before pushing. The new ids are written down before any row moves, so a crash part-way is finished with the same ids. Before this, a row filed directly as shared took the local counter, and two spokes filing into one project made the same id: the second was merged into the first as an edit. Each `ids.alloc` asks past the spoke's highest local id of the project (`past`); a hub refuses (`too_large`) one request that would move its counter more than its `max_id_advance` quota ahead (10,000 by default, never below 1,000). The quota is not told to clients, so a spoke whose local ids run further ahead steps the counter up first, 1,000 a request (`alloc_stepped`, `ID_STEP`, `crates/spoke/src/cmd_publish.rs`): one id past the counter says where it is, then one id at most 1,000 on, stopping where the ask fits; the ids the steps hand out are at or below the spoke's own and are gaps. An ask is at most 1,000 ids (`MAX_IDS`); a publish of more asks in parts.
- **The synced cache** (`crates/spoke/src/hub_cache.rs`, wsp-465). A spoke keeps its own rows whole, as files the import door writes, so `ls`, `show`, `wip` and `worklist show` read them like any local row. A row is its own when it was made here, is leased here, or is allocated to its user. Every other row is a head: title, status, holder and allocation in `$WSP_STATE/hub/heads.json`, shown in `ls` with no body, and never pushed back. `wsp show <id> --fetch` makes one whole, as does leasing or allocating it (`classify`, `crates/spoke/src/hub_cache.rs`): the stub stays until the hub's first record of the row is written over it in one atomic write (`Door::import_over`, `crates/engine/src/door.rs`), and the cache entry goes after, so `wsp show` finds the head or the row at every step and a turn the hub cuts short leaves the head. The worker follows the hub's event feed and keeps its position in `stream.json`; one that starts further than 100 events behind (`GAP`, `:42`) resumes from the head and lets the heads diff stand in for what it skipped.

## Private and shared workspaces, and publish

A workspace is a sync scope (d7).

| | Private | Shared |
| --- | --- | --- |
| Bound to | The local wsp | The hub |
| Who sees it | Its machine alone: its rows, lists, seats, asks and events never leave | Its members |
| Leases, allocation, routing | None; today's wsp | All of them apply |
| Named | `private` | `shared:<name>` |

- **New work is private.** `wsp add`, `wsp worklist new` and `wsp project add` file into the caller's workspace, private unless `--workspace shared:<name>` or `$WSP_WORKSPACE` says otherwise, the flag first, and a shared one needs a login and, as far as the spoke knows, membership of that workspace: what the hub last said (kept by the sync worker in `$WSP_STATE/hub/members.json`), or the hub asked at filing where that does not say yes and the connection is on (`crates/spoke/src/hub_members.rs`); a workspace known not to be the user's is refused before anything is written, online or off, and with nothing known (never connected here) and no hub to ask the filing goes ahead provisional and the hub refuses it at the sync. A child (sub-task, leg, piece) takes its parent's workspace (`src/record_workspace.rs:19`).
- **A shared row moved to a new id leaves no ghost** (`crates/spoke/src/hub_retire.rs`). `wsp mv` of a shared row X already on the hub, to Y, is followed at the next turn: Y is pushed (its first record naming X's head as its parent, so X's history is reached through Y), then X is retired on the hub (`refs.retire {workspace, subject: X, from: <X's head>, successor: Y}`). Nothing records the pending retire but `ids.json` (X → Y) and the hub's heads, read at every turn, so an outage or a crash only delays it; X is never kept as a head on the mover's spoke meanwhile. Answers: `retired` (or stale with no head) forgets X here; stale with another head retries from it next turn; `held` waits, said once a worker in `cycle.log` as `hub-sync: <X> is moved here to <Y>, but <X> is leased by <user | you on your other machine NAME>: it is retired on the hub once they let go, and is tried again each turn`; `invalid` waits for Y to reach the hub; any other refusal is said once and not asked again (`$WSP_STATE/hub/retire.json`). Every spoke follows the `retired` list of each `sync.heads` reply (and a `ref.retired` event wakes a turn): a stub of X goes, X → Y is recorded so `wsp show X` finds Y, and X is never pushed again; a whole X with edits not yet sent goes on as Y where Y is not here, and is kept (unpushed, said in the log) where it is.
- **Moving work across is `wsp publish`.** `wsp publish <row|list> --to shared:<name>` (`crates/spoke/src/cmd_publish.rs:195`) moves a private row, or a list with its member rows and their sub-tasks and pieces, into a shared workspace. The hub is asked first and a refusal changes nothing: each row takes a new id from `ids.alloc`, then is renamed and stamped `workspace:` (the old id keeps resolving through `ids.json`), and the sync worker pushes it on its next turn. A claimed row is published under a hub lease, so a refusal leaves every row as it was.
- **Refused:** a logged-out spoke, a row already shared, a sub-task or piece on its own, and a workspace the hub says the caller is not a member of. There is no unpublish in v1.
- **The hub scopes everything to membership** (the hub's `scope`). A user reads and writes a shared workspace they are a member of and nothing else; heads, moves and ids outside it are `forbidden`; an object is served only if a member workspace references it, so knowing a hash is no right to its bytes. An admin is no exception: an admin who is not a member reads none of the content. `crates/hub/tests/scope.rs` and the privacy gate (wsp-180, `tests/privacy.rs`) show a private row, list, seat and ask reaching no frame and no other user.
- **A list's slug is one name per workspace.** The hub keeps each workspace's subjects apart, so `run` in `shared:one` and `run` in `shared:two` are two lists; on a spoke that is a member of both (or has a private `run`), the one that arrives second is kept under `<slug>-<workspace name>` (`run-two`), and `$WSP_STATE/hub/lists.json` says which hub list that name stands for (`crates/spoke/src/hub_lists.rs`): its records and its drive lease go by the hub id. Two people making one slug in one workspace before either syncs: the hub holds the first pushed, and the second push is answered stale (or found diverged). A list never sent whose chain shares no object with the hub's (walking the hub head's parents meets none of the list's own journaled records) is another list, not a divergence: the second spoke sends its own under a new hub id, `<slug>-<user>` (a number after it where taken), takes the hub's under `<slug>-<workspace name>`, and says once in `cycle.log`: `hub-sync: <slug> in <ws> was made on the hub by someone else too before this spoke sent yours; theirs is kept here as <slug>-<workspace name>, and yours goes to the hub as <slug>-<user>`. A divergence of a list sent before is reconciled as ever.
- **Workspaces and members** are made from an admin's spoke: `wsp hub workspace add <name>` and `wsp hub member add|rm <ws> <user>` (`crates/spoke/src/cmd_hub.rs`).

Open: whether shared work can be taken back to private (v1 says no), and whether new work should stay private by default (it does, as proposed in d7).

## Leases and offline work

A row in a shared workspace is moved by one user's seat at a time, and the hub says which.

- **Taking.** `lease.take` before `wsp claim` (so before a spawn) and before `wsp start` answers a fencing token and an expiry, or refuses `held`, naming the user whose spoke has it, or `forbidden` for a row allocated to someone else (`crates/spoke/src/hub_lease.rs:112`; the hub's side is `Hub::take_row_lease`, the hub's `leases`). The token and the hub's expiry are written into the local claim, so the local expiry pass and the hub agree. Every row lease taken is also kept in the spoke's book (`rows` in `$WSP_STATE/hub/drive.json`) with its token, since `wsp start` makes no claim: a claim's lease goes back when the claim ends; one no claim holds goes back when the work is over (`done`, `park`, a landing: by the verb, else at the worker's next turn), is not renewed (no seat holds it), and is what `wsp hub disable` parks and gives back like a claimed one.
- **Per machine.** A lease is held by a user *on a machine*. Every hello names this machine, `machine: {id, name}` (`crates/spoke/src/hub_client/machine.rs`): the id is random, made once at the first dial and kept in `.config/wsp/machine.json` under the hub home (`$WSP_HUB_HOME`, else `$HOME`), beside `hubs.json` and not in it, so a logout and a new login leave it as it was; a sandbox, with a hub home of its own, is a machine of its own. The name is the host name (`hostname()`), held to 256 bytes with no control character. The hub refuses the same user on another machine `held` (take, renew, release) and its refusal names the user only; the machine is in its text, which the spoke reads (`other_machine`, `crates/spoke/src/hub_lease.rs`) to say `<row> is leased by you on your other machine <name>, not this one: release it there, or let its lease run out` (`… on another machine of yours, not this one: <the hub's text>` where the text names none). A spoke whose id can be neither read nor made names no machine, and the hub holds its leases by user alone, as before machines.
- **Length.** A lease runs 7 days from its take or last renewal (`lease_days` in the hub's config, default 7, at least 1).
- **Renewing.** While the holder seat is alive and the claim has been as it is for an hour, the daemon sends `lease.renew` and moves `expires` to the hub's answer (`renew_due`, `crates/spoke/src/hub_lease.rs:198`). Only the hub's word extends a claim that has a hub token.
- **Expiry.** The hub releases a lease past its TTL and announces `lease.expired` (`expire_leases`, the hub's `leases`). The spoke that held it lets go the way `wsp despawn --lost` does, the checkpoint kept in the tree (`follow_expired`, `crates/spoke/src/hub_lease.rs:467`).
- **Fencing.** A shared row's verdict and its landing go to the hub as `row.reviewed` and `row.landed` event objects carrying the claim's token (`push_verdict`, `crates/spoke/src/hub_lease.rs:257`). The hub refuses `fenced` one under a token that is no longer the row's current one; the spoke then lets go of the claim, and the row stays as its new holder left it.
- **Allocation.** `wsp allocate <row|list> <user>|none` (`crates/spoke/src/cmd_allocate.rs:61`) writes a `for:` naming the user whose agents may take the work, on any spoke that user is logged in on. A row's own `for:` wins, else its list's (`allocated_to`, `:22`). A shared row allocated to another user is refused at start, claim and spawn on this spoke before the hub is asked (`allocated_elsewhere`, `:31`), and the run skips it as running elsewhere. A private record cannot be allocated.

**Offline.** A spoke whose hub is unreachable keeps working on the rows it holds.

- Every object it makes for a shared workspace is kept in order in `$WSP_STATE/hub/journal/` until the hub has it (`crates/spoke/src/hub_journal.rs`); a claim whose lease is in date is not touched while the hub is away.
- On reconnect each row is settled by the lease it was made under. Renewed under the same token, the row fast-forwards. Refused, the claim is released and the lease taken again: granted, the row is pushed. Held by another user meanwhile, the objects go to the hub as a **side chain** (put, no ref moved), so this spoke's verdict and landing never reach the hub; its code is still on its git branch, which nothing here touches.
- Both users are told. The old holder's spoke records the side chain locally (`$WSP_STATE/hub/side.json`, a line in `cycle.log`) and sends a notice to the hub, which the new holder's spoke takes (`Side`, `notice`, `crates/spoke/src/hub_journal.rs:191`, `:370`).
- A push a crash cut short is replayed whole, with no object twice (`Journal::replay`, `:166`): a put is idempotent by hash.

The lease is the bound on offline work: a person can go as far as their leases last and no further without risking the side chain.

## List driving

A worklist is driven by the spoke it is allocated to (d5), and only one spoke at a time advances it.

- **The drive lease.** A shared list is advanced only by the spoke holding the hub lease `drive:<list>` (`drive_row`, `crates/spoke/src/hub_lease.rs:478`; the decision is `drive`, `:588`). The daemon renews it while it ticks (`renew_drives`, `:704`); a list no longer running here, done or gone or made private, lets its lease go.
- **Members run where they are held.** The driver leases each member row before spawning it. A member another user's spoke holds runs on that spoke, and that spoke, which does not drive the list, opens the verifier for the member it holds and touches nothing else. The spoke's drive gate (`Spoke::drive`, `crates/spoke/src/spoke.rs`, which the run's `driven_here` asks through the add-on interface) says in `cycle.log`, once per change, who drives a list.
- **A spoke without the drive lease never advances the list.** It sees the list and its members through the cache and can read who drives it; the barrier, verification and closing steps run on the driver alone.
- **Private lists** are driven by their own wsp as always.

## Login and tokens

Each person has their own token and the hub derives who they are from it, never from what a client says about itself (the hub's `auth`).

- **Resolving a hello.** A token whose hash is an active token record of an active user names `person:<user>`. The hub's bootstrap token (`api.token` in its data directory, made on first start at 0600) names the hub itself while the hub has no active admin, and may do one thing: add the first admin. Anything else is refused `unauthorised`, saying no more; an unknown token and a revoked one read alike. A request whose `by` is another principal is `forbidden`, as in the daemon.
- **The first admin.** `wsp-hub admin init --config <file> --admin <name>` makes it on the hub's host and prints its token once (the hub's `admin`). The hub keeps the hash and nothing else; the token is written nowhere.
- **More users.** From a logged-in admin's spoke: `wsp hub user add <name> [--admin]`, `user ls`, `user revoke <name>`, and `wsp hub token <name>`, which issues a new token and revokes the old ones. The token is minted on the spoke and only its hash is sent; it is printed once and is in no log, command, event or file (`crates/spoke/src/cmd_hub.rs`).
- **Logging in.** `wsp login <hub-url>` (`crates/spoke/src/cmd_login.rs:292`) reads the token from the terminal prompt with echo off, or from stdin, never from the command line. It dials the hub, says hello and, on `welcome`, writes `~/.config/wsp/hubs.json` (`url`, `token`, `user`, `at`, and `ca` for a private CA) at mode 0600; a file that already exists wider is refused, naming it. `user` is the name the hub's `welcome` gave the token. A wrong token, an unreachable hub or a refused certificate writes nothing. One hub per wsp in v1; a second login replaces the first and says so. `wsp login <hub-url> --github` reads no token: the hub runs GitHub's device flow (`login`, `login_prompt`, `login_done` frames), the address to open and the code to enter are printed, and the user and token the hub hands back are written to the same file the same way; the token is never printed, and a refused or expired login writes nothing. `wsp logout` disables the connection (`wsp hub disable`) and then removes the file; `wsp hub status` prints the URL and user, never the token, and whether the connection is on, what the disconnect parked and what is unsent; `wsp whoami` asks the hub which principal the token names (`src/cmd_whoami.rs`), and a spoke with no login dials nothing.
- **From the environment.** `$WSP_HUB_URL`, `$WSP_HUB_USER` and `$WSP_HUB_TOKEN` (or `$WSP_TOKEN`) replace the file, for tests and machines (`crates/client/src/credential.rs`).
- **A token never leaves its dial.** `scrub` takes it out of anything a dial said (`crates/spoke/src/cmd_login.rs:77`), and the only child process login starts is `stty` with fixed arguments.

A connection keeps the principal it was welcomed as until it closes; a revoked token is refused at the next hello.

## Routing and the user primary

`wsp tell` reaches a row, a seat or an address (`src/address.rs`). The hub carries it past the one machine.

- **Addresses.** `primary` is this machine's own primary seat. `primary:<user>` is that user's primary: on a spoke logged in as them, the local `primary` seat; for anyone else, a remote the hub routes (`src/address.rs:67`, `parse`; `:187`). `seat:<row>` and `governor:<list>` are routed by who holds the row's lease or the list's drive lease when the holder is another user's spoke.
- **How the hub resolves one** (the hub's `messages`). `seat:<row>` goes to the holder of the row's lease (`row:<row>`), unexpired; `governor:<list>` to the holder of `drive:<list>`; `primary:<user>` to that user, live on the hub. The message is queued for the user, and the first of their spokes to `msg.take` and `msg.ack` it has it. The sender must be a member of the workspace the lease was taken in, or share one with the user whose primary it names: knowing a row's id is no right to reach its holder. A reply (a message whose `re` names one the hub delivered to the sender) goes back to that sender whatever `to` says. What nothing resolves is refused `not_found`, naming the address.
- **The queue** is a revisioned text per user (`hub-inbox:<user>`), each change a compare-and-swap. `msg.take` changes nothing, so a spoke cut off before its ack is handed the same messages again; `msg.ack` removes them. A queued message is announced on the event feed so the recipient's spoke hears it has mail.
- **Locally**, `primary:<user>` for the user logged in here is spooled and ordered like a governor's under its slot; for another user it is one message through the hub, once per level (`route_to_primary`, `src/wake.rs:691`, called from `:253`). A tell with no login is refused, naming `wsp login`.
- **Escalation.** A question escalated past `primary:<user>` is that user's: Needs you shows it `for <user>`, so it says whose it is (`for_user`, `src/attention.rs:378`, used at `:365`).

## Hosting with TLS (wsp-461)

The hub (`wsp-hub serve --config <file>`) serves TLS when its config names a certificate, and a hub on a public endpoint must: it refuses to start bound to an address that is not loopback without one (`Config::tls_required`, the hub's `config`). No host is written in the code or the tests; the hub is whatever the config says, and a tailnet stays optional.

```json
{
  "data_dir": "/var/lib/wsp-hub",
  "bind": ["0.0.0.0"],
  "port": 7489,
  "peers": ["0.0.0.0/0", "::/0"],
  "tls": { "cert": "/etc/wsp-hub/fullchain.pem", "key": "/etc/wsp-hub/privkey.pem" }
}
```

- `tls.cert` is the PEM certificate chain and `tls.key` its private key (relative paths are read from the config's directory). With `tls` every connection is TLS, loopback included.
- `peers` is the hub's own list of CIDR blocks it admits; a public hub names `0.0.0.0/0` and `::/0`. It is the hub's alone: the daemon's server admits loopback and the tailnet and nothing else, and has no TLS.
- Loopback is always bound; every `bind` address must be in `peers`. A key the file does not know is an error, so a misspelt `peers` does not quietly leave the default.

**The URL.** A client names a hub by `tls://host:port` for TLS, which is the form for any hub that is not on loopback or a private network. `tcp://host:port`, or a bare `host:port`, is plain TCP, as before: the user's token crosses it in the clear. Any other scheme (`https://` too: the protocol is not HTTP) is refused, and a port is required.

**Trust.** A `tls://` hub's certificate must be for the URL's host and chain to the platform's root certificates (`crates/spoke/src/hub_client/tls.rs:34`). A private CA (a test, a self-hosted hub) is *pinned* with a PEM file, named by `--ca <file>`, `$WSP_HUB_CA`, or `"ca"` in `~/.config/wsp/hubs.json`: the client then trusts that CA's certificates and no other root. A certificate it refuses ends the dial as `Silent::Tls`, naming the fault (`invalid peer certificate: UnknownIssuer`, `... not valid for name ...`); the user's token is not sent.

**Deploying it.** The container image, the compose file and the step-by-step recipe (certificate, firewall port, backup, upgrade, first login) are the hub repository's (its `docs/hub-deploy.md` and `deploy/hub/`). Hosting and network are configuration, and no machine name or address is a literal anywhere in code, docs or plans (d5).

## What a desktop app reads

Machine-readable output for an app that runs `wsp` and reads the feed's `Row` (`crates/store-contract`). What crosses the add-on interface is engine-agnostic: `SharedWork::row_facts` answers `RowFacts { held_by, held_on, held_until, held_here, head_only }` per shared row (`crates/engine/src/addon.rs`), and the engine turns it into fields.

- **Who holds a row, head-only, mine (feed).** Every shared row in the feed (and `wsp ls --json`'s rows, both from `mirror::row_half`) carries the string fields `mine` and `head_only` (`"true"`/`"false"`), and `held_by` (a user), `held_on` (a machine's name) and `held_until` (ISO 8601 UTC) where known. A private row carries none of them. They ride on the rows the feed sends and never on the row a hub is sent (`mirror::shared_row`). A change to them re-reads the rows: the add-on's `facts_stamp` is part of the rows half's stamp.
- **The same in `wsp show <id> --json`**, as keys on a shared row: `mine` and `head_only` booleans, `held_by`, `held_on`, `held_until` strings or `null`.
- **Where the holder comes from** (`Spoke::row_facts`, `crates/spoke/src/spoke.rs`), with no dial: the lease events the sync worker hears on the hub's stream (`lease.taken`, `lease.released`, `lease.expired`, each with holder, expiry and, from a hub that keys leases by machine, `machine {id, name}`), kept in `$WSP_STATE/hub/holders.json` (`crates/spoke/src/hub_holders.rs`); else the user a refused take named (`drive.json`'s `elsewhere`, the user alone); and this spoke's own leases (its book and its claims' tokens), which are `held_by` this user, `held_on` this machine, until their expiry. Not known: a lease taken before this spoke last heard the stream (a worker resuming at the hub's head after a gap skips the events between; the stream's opening state carries no lease for a user, and the hub's admin-only `state` has leases but no machine), and anything while no worker runs. A lease past its own expiry reads as gone.
- **"Mine"** is defined once, `addon::mine`: leased by this user on this machine (`held_here`), or allocated (`for`) to this user.
- **Head only** is a row kept as the hub's head (`heads.json`): `wsp show <id> --fetch` brings it whole.
- **Login prompt.** `wsp login <url> --github --json` prints, when the hub sends the device-flow prompt and before it waits, one line on stdout: `{"prompt":{"code":"ABCD-1234","expires_secs":900,"verification_url":"https://github.com/login/device"}}`; on success the usual `{"url","user","replaced"}` line follows. The sentence on stderr is unchanged.
- **Account facts in `wsp hub status --json`**, beside `logged_in`, `url`, `user`, `at`, `ca` and `connection`: `method` (`"token"` or `"github"`, which `wsp login` now writes into `hubs.json`; `null` for an older file), `workspaces` and `workspaces_at` (the shared workspaces the hub last said this user is a member of, from `members.json`; `null` where none is kept for the user), `machine {id, name}` (what each hello names; `id` `null` before the first dial), and `admin`: `true` or `false`, what the hub's last `welcome` said of the user (the welcome's additive `admin` field, from the users table on the hub; the hub's `docs/hub-deploy.md`, "Admins"), kept in `.config/wsp/welcome.json` under the hub home, beside `hubs.json` and not in it, as `{url, user, admin, at}`: `wsp login` drops what the last login was told and keeps its own welcome's, each dial the sync worker makes keeps its welcome's, `wsp logout` removes it, and status reads it only for a login of the same url and user (`crates/spoke/src/hub_client/login.rs`, `keep_welcome`, `kept_admin`). `null` where nothing is kept for the login (a GitHub login before the worker's first dial) or the hub is older than the field and did not say; never a guess from a refusal. The human `wsp hub status` does not print it, as it prints neither `workspaces` nor `machine`. The token is never printed.
- **Park preview.** `wsp hub disable --dry-run [--json]` and `wsp logout --dry-run [--json]` say what the disconnect would do, doing and dialling nothing: `{"dry_run":true,"logged_in":true,"off":false,"park":[{"row":"s-1","status":"doing"}],"ending":[{"row":"s-1","seat":"cpd-s1"}],"leases":["s-2","drive:run"],"unsent":0}`. `park` is the rows it would park, `ending` the agents it would ask to end at the end of their turn (their rows' leases are held until they are gone, so they are not in `leases`), `leases` what it would give back if the hub answers, `unsent` the journal entries it would send first. Every list comes from the function the disable acts on (`in_flight`, `agents_to_end`, `leases_to_give_back` in `crates/spoke/src/hub_switch.rs`). A park the row refuses, or an agent whose ending cannot be arranged, is known only when it is tried. A logout with no login: `"logged_in":false` and empty lists.

## Doctor

**What `wsp doctor` says of the hub** (wsp-194; `health`, `crates/spoke/src/hub_sync.rs:398`, which the doctor asks through the add-on interface, `addon::get().health`). One line for the local API, naming the addresses `api.json` lists (`api_health`, `src/mirror.rs:1132`). Then, for a wsp with no login, one line: `not logged in to a hub (standalone)`, and nothing else about hubs. For a spoke: the hub URL and user (from `hubs.json`); the certificate's expiry (read from a handshake with the URL's host, so a `tcp://` hub says it has none; a week or less is a warning); the last good sync and the last failure with its reason (`$WSP_STATE/hub/sync.json`, which the worker keeps); the journal's length; the row leases the claims here hold and the soonest expiry; the drive leases held. A lease within a day of its expiry whose seat is not alive is a warning, since nothing renews it. No host or address is a literal: everything is read from `api.json`, `hubs.json` and the worker's files.

## Later

Nothing here is built, and none of it is the design of record. It is what the first, retired design (one server for an org of groups; `git show fdade73:docs/multiplayer.md` has it whole, with its phases and breakdown) held that may come back on the hub, in the order it is likely to matter.

- **Groups and roles.** Groups, group leads and watchers above the hub's users and shared workspaces; today a workspace has members and the hub has admins.
- **Budgets and spend.** Spend charged to a shared workspace, with budgets that refuse a spawn past them; `spent.jsonl` would have to move into a store first.
- **Single sign-on.** A way to issue tokens from an identity provider; it would replace only how a token is issued.
- **Taking shared work back to private**, and a recorded take-over of another user's row.
- **A fence between users on a shared host.** A hub never hosts seats, so this matters only if two people share one machine.
- **Scale.** Several hub processes and a log per workspace, if one hub's single SQLite stops being enough.
